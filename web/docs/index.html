Run Tare.

Everything needed to go from a clone to a disputed seller, a refused payment and a clean one, on Kite testnet.

What Tare is

Tare is an independent check of what an x402 data seller delivered. It pays a data seller over x402 on Kite testnet (with Kite Passport, or a capped testnet key while Passport cannot pay uncatalogued sellers), reads the seller's own promises with SERV Reasoning, both the 402 advertisement made before payment and the note that comes with the delivery, and checks those promises against the delivered rows in code. Every check becomes a receipt with evidence, and every seller has a record: a seller whose claims fail is held, and the agent stops buying from it before any payment.

Not a spending policy. A spending policy decides before paying, from the amount, merchant and budget. Tare checks after delivery, from the rows. Kite Passport's capped session is the spending limit; Tare verifies what it bought.

Code, not SERV, counts and decides. The model id is gpt-5.4-mini-serv-multipath; it only extracts claims: four from the main prompt, and a time window (max_age_hours) from a second prompt that runs only when the seller mentions time. Code drops any claim the seller's text does not support: a count must be a number the seller states exactly, not "up to 20" or "10,000+".

Quick start

git clone https://github.com/Ritapossible/Tare && cd Tare
npm ci
npm test                        # SERV and the payment rail are faked; no network
cp .env.example .env            # add SERV_API_KEY
node scripts/serv_check.mjs     # one real SERV call, production client
npm run app                     # console on http://127.0.0.1:4020

SERV key

Create a key at console.openserv.ai and put it in .env as SERV_API_KEY. The $5 starter credit pays for SERV inference only; it never funds a payment.

node scripts/serv_eval.mjs runs nine ordinary and six adversarial seller texts against the real model and reports accuracy and safety. Last live run (10 Nov, final code): accuracy 9/9, safety 6/6. Requests declare SERV's serv_disable_content_filter tool, because the default filter refused plain seller texts. SERV's Prompt Guard is deliberately off: it would turn a seller's injection attempt into a SERV failure, so the seller would be paid but not held.

Kite testnet

Kite Passport CLI 6.13.1. Run these once, in order. You approve the session with your passkey yourself; Tare never automates it.

curl -fsSL https://cli.gokite.ai/install.sh | bash
kpass signup init --email <you>      # or: kpass login init / login verify
kpass sandbox on                     # testnet mode
kpass wallet address
kpass agent register --type service-tester
kpass session create --separate --task-summary "tare receipt check" \
  --max-amount-per-tx 0.05 --max-total-amount 1 --assets pieUSD --ttl 1h --no-browser

The production faucet is disabled in 6.13.1. Testnet pieUSD came from the faucet on Kite's dev Passport backend; the steps are in docs/RUNBOOK.md.

Asset: pieUSD 0x38129cf4CE5E183eFF248F42A7D345Bb1B47621A (18 decimals), network eip155:2368, facilitator https://facilitator.pieverse.io/v2.

Payment rail

Two rails behind one interface, chosen with TARE_PAYMENT_RAIL:

  • kpass (default): Kite Passport pays inside a passkey-approved session (0.05 per payment, 1 in total, 1 hour).
  • x402-direct: Tare signs the standard x402 payment with a testnet-only key (node scripts/x402_wallet.mjs), and the Pieverse facilitator settles it. Tare refuses to sign anything but testnet pieUSD on eip155:2368, at most 0.05 per payment and 1 in total over the key's lifetime.

Kite Passport currently pays only sellers listed in Kite's service catalog (host_not_in_executable_catalog for Tare's sellers on 10 Nov 2026), so the published run used x402-direct: payer 0x7979989aD2A57dC6bBf28fFB120b18aC0aB10895 (Tare's testnet key), payee 0x9Ef47eA89403c6a2637271B655b0C5b99c68C447 (the owner's Passport wallet). Its settlements, verified on Kite testnet:

Add Tare to your agent

// npm install github:Ritapossible/Tare   (SERV_API_KEY in the environment)
import { verify, tareFetch } from "tare";
const r = await verify(sellerText, rows);   // verdict: clean | dispute | unverifiable
const receipt = await tareFetch(sellerUrl);  // pay, check, record; held sellers are refused

verify never pays: it reads the seller's own text with SERV and checks your rows in code. tareFetch is the full buyer, as in the CLI, and keeps its store in ./data/store.json.

Console

npm run app serves this site with a live API on 127.0.0.1:4020. The Buy buttons only accept the sellers in sellers.json; the browser cannot send an arbitrary URL. From the command line:

node scripts/reset.mjs        # clean slate for a demo take
node scripts/buy.mjs a        # dispute, seller held
node scripts/buy.mjs a        # stopped, no payment attempted
node scripts/buy.mjs b        # verified (status: clean)
node scripts/publish.mjs      # state.json, records.json and badges for the hosted site

If a payment's outcome is unknown (a timeout after signing), the receipt stays pending and the seller is refused until you check the payer's wallet on the explorer and run node scripts/resolve.mjs <receipt id> not-paid or paid <tx hash>. A hash entered this way is marked as entered by the operator.

Rules

RuleFails when
shapeThe body is not JSON with a string prose and an array of objects rows.
countA count is claimed and differs from the row count (or the unique-id count, when uniqueness is claimed).
uniqueUniqueness is claimed and some ids repeat.
fieldsFields are named and some row lacks one.
no_nulls"No nulls" is claimed and a checked value is null or empty.
freshA time window is claimed and some row's ts is missing, unreadable, older than the window, or more than 5 minutes in the future.
advertised:<rule>The same rules, applied to the claims in the seller's 402 advertisement. A missing advertisement is noted and never changes the verdict.

A seller that takes payment and then returns an error is a shape dispute: the settlement hash is kept and the seller is held. Any failure is a dispute. No failure but no count claim is unverifiable: the seller is held, because a promise that claims nothing cannot be checked. A human can release a hold with node scripts/unblock.mjs <origin>.

Security

  • The local API binds to 127.0.0.1, checks the Host header (against DNS rebinding), requires a custom header plus JSON (so another website cannot trigger a buy), and only buys sellers listed in sellers.json.
  • Seller prose is untrusted: it is escaped on every page and wrapped in <prose> tags for SERV.
  • kpass is spawned with an argument list, never through a shell.
  • The model never sees the rows and has no verdict to give; code drops any claim the seller's text does not support.
  • Spending caps: 0.05 per payment and 1 in total, testnet pieUSD on Kite testnet only. A held seller is refused before any payment is attempted.
  • The direct rail's testnet key lives in data/ (gitignored, mode 0600) and is never printed.
  • scripts/publish.mjs refuses to publish any hash that is not a 0x-prefixed 32-byte value, or any payment still pending.

Seller records

Every check becomes a public seller record: held (a check failed, with the evidence) or in good standing. Publishing writes the feed to /records.json, the Check a seller page reads it, and verified sellers get a badge at /badges/<host>.svg.

Another agent opts in by trusting the feed. A seller held there is stopped before payment:

TARE_FEEDS=https://tare-agent.vercel.app/records.json node scripts/buy.mjs <seller url>
# override for one buy, on purpose:  --allow-feed-hold

An unreachable or malformed feed never blocks a buy, and every feed problem is written on the receipt. There is no global blacklist: agents choose which publishers to trust, and a record covers one origin only.

Paid lookups. The same seller template can sell the feed at 0.001 testnet pieUSD per lookup (steps in sellers/README.md). An agent pays for lookups only with TARE_PAY_FEEDS=1; the payment uses the same rail and caps as a buy, is cached for 5 minutes, and its hash is written on the receipt. People check for free on Check a seller.

Deploy to Vercel

The site is static: no build step, no server functions.

  1. Import Ritapossible/Tare in Vercel.
  2. Set Root Directory to web, Framework Preset to Other, and leave the build command empty.
  3. Deploy. After a live run, run node scripts/publish.mjs, commit web/data/state.json, web/records.json and web/badges/, and push; Vercel redeploys with the real receipts.
