Overview

Tare is an independent check of what an x402 data seller delivered. With x402 an agent pays a seller and gets the data back in the same response, along with the seller's own description of it ("1,240 unique records, no nulls"). Nothing compares that description to the data. Tare does.

Not a spending policy. A spending policy decides before paying, from the amount, merchant and budget. Tare checks after delivery, from the rows. The two work together: a cap limits what an agent can pay, and Tare checks what that payment bought, whichever wallet signed it.

Three systems, strict lanes. SERV Reasoning reads the seller's words and returns typed claims. Tare's code counts the rows and decides. The payment rail pays, inside caps. The model never sees the rows, never returns a verdict and never pays.

How a buy works

Every buy runs these steps in order, one buy at a time. Steps 1 to 4 can stop a buy before any money moves.

  1. Replay check. A buy with a request id seen before returns the original receipt. It never pays twice.
  2. Local seller record. If the seller's origin is held, the buy is refused before any payment.
  3. Pending check. If an earlier payment to that origin has an unknown outcome, the buy is refused until a person resolves it.
  4. Trusted feeds (optional). If a feed the operator trusts holds the seller, the buy is refused, unless the operator allows it on purpose with --allow-feed-hold.
  5. 402 advertisement. An unpaid request reads the seller's resource.description: the promise it makes before any money moves.
  6. Pay. The payment rail pays 0.001 testnet pieUSD over x402. The receipt is written as pending first, so a crash can never lose a payment. The settlement hash comes from the PAYMENT-RESPONSE header and is never made up.
  7. Read. SERV Reasoning reads the delivery note and the advertisement and returns claims. Code drops any claim the seller's text does not support (grounding).
  8. Check. Code counts rows, distinct ids, fields, empty values and timestamp ages, and checks every claim from both sources.
  9. Record. A dispute or an unverifiable delivery puts the seller on hold. The receipt keeps the evidence.

Quick start

Requires Node 22 or newer and a SERV Reasoning API key.

git clone https://github.com/Ritapossible/Tare && cd Tare
npm ci
npm test                        # SERV and the payment rail are faked; no network
cp .env.example .env            # add SERV_API_KEY
node scripts/serv_check.mjs     # one real SERV call, production client
npm run app                     # console on http://127.0.0.1:4020/app

To make real payments, set up a payment rail (Payment rails) and deploy two sellers (Demo sellers). Then:

node scripts/reset.mjs    # clean slate (keeps the lifetime spending ledger)
node scripts/buy.mjs a    # dispute, seller A held
node scripts/buy.mjs a    # stopped, no payment attempted
node scripts/buy.mjs b    # verified

SERV Reasoning

Create a key at console.openserv.ai and put it in .env as SERV_API_KEY. The $5 starter credit pays for SERV inference only; it never funds a payment.

Modelgpt-5.4-mini-serv-multipath, reasoning_effort: low
OutputStrict JSON schema, 400-token cap. Any field outside the schema is dropped unread.
Main promptFour claims: claimed_count, unique, fields, no_nulls. sha256 7b5d603d7c140d3cf34afc3b525cac2e7ddb4bd001a092f26fa28c89437bec86
Freshness promptOne claim, max_age_hours. Runs only when the seller's text mentions time. sha256 b7089fef4ceba1244340c9c975202a8630356e20298c6d3fa0b81fe59facaa1c
InputOnly the seller's text, inside <prose> tags. Any <prose> tags the seller hides in its own text are stripped first. The rows are never sent.
RetriesAn invalid answer is retried once. A second invalid answer is SERV_INVALID; an API error is SERV_API. Either one leaves the receipt paid, unchecked.

Why two prompts. Adding the time window to the main prompt made SERV's content filter refuse far more short texts (9 of 12 against 3 of 12), so freshness became its own call and the main prompt was left unchanged.

SERV platform tools. Requests declare serv_disable_content_filter by default (TARE_SERV_TOOLS), because the default filter refused plain seller texts such as "Here is your data.". serv_prompt_guard is deliberately off: it blocks injection-looking text, which Tare would have to record as a SERV failure, so the seller would be paid but not held. Without it, the same text is read, checked and disputed.

Grounding

SERV is good at reading phrasing and bad at admitting a text says nothing. On real x402 service descriptions it invented counts, "unique" and "no nulls". So code keeps a claim only when the seller's own text supports it. Code may drop a claim; it never adds or changes one. Dropped claims are listed in the receipt's notes.

ClaimKept only if the seller's text…
claimed_countstates that exact number, in digits or words (English or Spanish). Not as a bound or approximation ("up to 20", "10,000+", "~2", "about 200"), and not inside a price, decimal, percentage, time or name ("$0.002", "7%", "23:59", "HIP-4"). A lone "one" is not a count.
uniquesays unique, distinct or no duplicates.
no_nullsmentions nulls, empty, missing or blank values.
fieldstalks about fields or columns, and names every field it claims.
max_age_hoursnames that window explicitly ("last 24 hours", "this week", "today"). "Latest", "real-time" or "~2 days" name no window.

Checks

All checks are plain code. Rows are expected as {"prose": "...", "rows": [{...}, ...]}; ids are read from each row's id and times from its ts.

RuleFails when
shapeThe body is not JSON with a string prose and an array of objects rows, or the seller took payment and returned an error.
countA count is claimed and differs from the row count (or from the unique-id count, when uniqueness is claimed).
uniqueUniqueness is claimed and some ids repeat.
fieldsFields are named and some row lacks one.
no_nulls"No nulls" is claimed and a checked value is null or empty. Checked fields are the named ones, or every field if none are named.
freshA time window is claimed and some row's ts is missing, unreadable, older than the window, or more than 5 minutes in the future (measured at delivery time).
advertised:<rule>The same rules, applied to the claims in the seller's 402 advertisement. A missing advertisement is noted and never changes the verdict.

Verdict. Any failed rule is a dispute. No failure but no count claimed anywhere is unverifiable: a promise that claims nothing cannot be checked, so the seller is held. Steering the model into empty claims gets a seller held, not trusted. Otherwise the delivery is verified.

Receipts

Every buy, including a refused one, produces a receipt. These fields are the evidence; the hashes let anyone repeat a check.

FieldMeaning
statusSee Statuses.
origin, urlThe seller. Records are keyed by origin (new URL(url).origin), never by a name the model returned.
tx_hashThe settlement hash from PAYMENT-RESPONSE, or null. Never invented. tx_hash_source: "operator" marks a hash a person entered after checking the explorer.
payment_railkpass or x402-direct.
body_sha256sha256 of the delivered body's exact bytes.
prompt_sha256sha256 of the system prompt used to read the promise.
promiseThe delivery note, word for word.
advertisedThe 402 advertisement, word for word.
claims, advertised_claimsWhat SERV read from each, after grounding.
count, unique_count, oldest_age_hoursWhat code measured.
failedThe rules that failed, e.g. count, advertised:fields.
serv_notes, ad_notes, feed_notes, body_notesHow the receipt was read: claims dropped by grounding, advertisement problems, feed results and paid lookups, how the body was hashed.
reason, errorWhy a buy was refused, or what went wrong. Shown with a plain sentence.
seller_identityThe seller's Kite agent DID from Kite's directory, or null (see identity_notes).
request_id, idempotency_keyReplay protection: origin|request_id. The payment key is derived from it, so one request can never pay twice.

Trusting a feed. Another agent opts in. A seller held in a trusted feed is stopped before payment:

TARE_FEEDS=https://tare-agent.vercel.app/records.json node scripts/buy.mjs <seller url>
# override for one buy, on purpose:  --allow-feed-hold

An unreachable or malformed feed never blocks a buy, and every feed problem is written on the receipt. Malformed records are ignored one by one. There is no global blacklist: each operator chooses which feeds to trust, and a record covers one origin only.

Paid lookups. The same seller template can sell the feed at 0.001 testnet pieUSD per lookup (steps in sellers/README.md). An agent pays for lookups only with TARE_PAY_FEEDS=1; the payment uses the same rail and caps as a buy, is cached for 5 minutes, and its hash is written on the receipt. Tested live on 10 Nov 2026: a fresh agent paid one lookup (0x217a85b7ee1563555664308ca6800510efb22a4a403ceb159dad4ee15c8d3d20), saw seller A held, and paid seller A nothing. People check for free on Check a seller.

Verifiable identity

Both checks use Kite Passport's public agent directory.

Who published a record. records.json is signed by Tare's publisher key (0x9C81aD8f2B0e3Ff97604F4a3CFCbd6771Df89485): EIP-191 over a sha256 of the feed's canonical JSON. An agent pins the publisher it trusts; a pinned feed whose signature does not check out is ignored, and the receipt says why.

TARE_FEEDS=https://tare-agent.vercel.app/records.json#0x9C81aD8f2B0e3Ff97604F4a3CFCbd6771Df89485
TARE_FEEDS=https://tare-agent.vercel.app/records.json#did:kite:<controller>:<agent>

With a did:kite: pin, the signer must hold one of that agent's active keys in Kite Passport (GET /v1/agents/<did>/signingKeys). Tare derives each key's address from Kite's published public key itself, and checks the validity window.

Who the seller is. Before paying, Tare looks the seller's origin up in Kite's agent directory and writes the result on the receipt and the seller record: the seller's DID, or "not registered". It is evidence only and never blocks a buy. Tare's demo sellers are not registered.

Linking the publisher key to a Kite DID needs the account owner's one-time Kite onboarding (a permanent identifier and KYC); the steps are in scripts/identity.mjs.

Kite testnet setup

Kite Passport CLI 6.13.1. Run these once, in order. You approve the session with your passkey yourself; Tare never automates it.

curl -fsSL https://cli.gokite.ai/install.sh | bash
kpass signup init --email <you>      # or: kpass login init / login verify
kpass sandbox on                     # testnet mode
kpass wallet address
kpass agent register --type service-tester
kpass session create --separate --task-summary "tare receipt check" \
  --max-amount-per-tx 0.05 --max-total-amount 1 --assets pieUSD --ttl 1h --no-browser

The production faucet is disabled in 6.13.1. Testnet pieUSD came from the faucet on Kite's dev Passport backend; the steps are in docs/RUNBOOK.md. For the direct rail, run node scripts/x402_wallet.mjs, fund the printed address with testnet pieUSD, and set TARE_PAYMENT_RAIL=x402-direct.

  • verify(promise, rows) never pays and needs no wallet. It reads the seller's text with SERV, grounds the claims and checks your rows in code. Rows that are not objects are a shape dispute without calling SERV. A SERV failure throws ServError (SERV_INVALID or SERV_API).
  • tareFetch(url) is the full buyer, as in the CLI: payment rail, seller records, trusted feeds. It keeps its store in ./data/store.json of the calling process.
  • Also exported: check, parseBody, measure, ground, extractClaims, RULES, PROMPT_SHA256, FRESHNESS_PROMPT_SHA256.

Security

  • The model never sees the rows and has no verdict to give; code drops any claim the seller's text does not support.
  • Seller text is untrusted: it is wrapped in <prose> tags for SERV (hidden tags stripped) and escaped on every page.
  • Spending caps: 0.05 per payment and 1 in total, testnet pieUSD on Kite testnet only. A held seller is refused before any payment is attempted.
  • Buys run one at a time with a request id, so a double click replays the receipt instead of paying twice. A payment whose outcome is unknown stays pending and blocks the seller until a person resolves it.
  • The local API binds to 127.0.0.1, checks the Host header (against DNS rebinding), requires a custom header plus JSON (so another website cannot trigger a buy), and only buys sellers listed in sellers.json.
  • kpass is spawned with an argument list, never through a shell. Tare never automates the passkey approval.
  • The direct rail's testnet key lives in data/ (gitignored, mode 0600) and is never printed.
  • Publishing refuses any hash that is not a 0x-prefixed 32-byte value, and any payment still pending.

Limits

  • After the payment, not before. x402 returns the data only after payment, so Tare cannot stop the first bad buy. It catches it, keeps the evidence and stops the next one. It does not refund.
  • Rows only. The checks need a delivery with rows. Most real x402 responses are arbitrary JSON; reading the 402 advertisement works on any x402 seller.
  • Per origin. Holds are keyed by origin, so a seller can move to a new domain. Receipts record a seller's Kite DID when it has one; keying holds by DID is the next step.
  • SERV can miss a window. In testing, "this week" was read as 168 hours in 2 of 3 calls. A missed window means freshness is not checked; it never invents one.
  • Real sellers promise little. Of 1,000 public x402 descriptions read on 10 Nov 2026, 11 stated a number of items and none said "unique" or "no nulls". Tare holds a delivery that promises nothing countable, and the badge goes only to sellers that state a promise and keep it.
