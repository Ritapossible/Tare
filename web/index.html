The problem

Agents pay first. Nobody checks the goods.

With x402 an agent pays a data seller and receives the body in the same response. The seller describes its delivery, "1,240 unique records, no nulls", and the agent moves on. Nothing compares that description to the rows. Budgets and allowlists cannot help: they never look at what came back.

Not a spending policy

Before the payment
vs after the delivery.

Spending limits answer "may I pay?" Tare answers "did I get it?" They are two halves of safe agent commerce. Kite Passport already caps the spend. Tare adds the half nobody checks.

Who decides

Three systems.
Strict lanes.

The model reads. The code verifies. The wallet pays. None of them can do another's job.

Guarantees

Built to fail closed.

Evidence on every receipt

Settlement hash, sha256 of the delivered body and sha256 of the prompt used to read the promise, so a check can be repeated.

No claim, no pass

A promise with no count is "unverifiable", not verified. Steering the model into empty claims gets a seller held, not trusted.

Rows never reach the model

SERV sees the prose inside <prose> tags and nothing else. Any tags the seller hides in its prose are stripped.

Held sellers are not paid

A held seller is stopped before any payment is attempted. The console's payment counter does not move.

Never invents a hash

Only a hash returned in PAYMENT-RESPONSE is stored or shown. Missing means "paid, no hash", never a made-up value.

One request, one payment

Buys carry a request id and run one at a time, so a double click replays the receipt instead of paying twice.

FAQ

Questions,
answered plainly.

Is Tare a spending policy?

No. A spending policy decides before a payment, from the amount, the merchant and the budget. Tare works after the delivery: it checks the rows a seller sent against the seller's own claims. It sits next to a spending policy. A spending cap limits what the agent can pay; Tare verifies what that spend bought.

How are payments made?

Over x402 on Kite testnet, with testnet pieUSD. Tare supports Kite Passport (kpass) as its payment rail, but Passport currently only pays sellers listed in Kite's service catalog. Until Tare's sellers are listed, the published run signs standard x402 payments with a testnet-only key, capped by Tare at 0.05 per payment and 1 in total, and the Pieverse facilitator settles them on Kite testnet. Every hash shown is a real Kite testnet transaction.

Does SERV decide anything?

No. SERV Reasoning (gpt-5.4-mini-serv-multipath) only turns the seller's prose into four typed claims. Counting, checking, recording and paying are all plain code. Any extra field the model returns, such as a "verdict", is dropped unread.

Why check after paying instead of before?

Because x402 only returns the body after payment. There is nothing to count before paying. What Tare guarantees is that a broken promise is caught, evidenced and acted on, so the agent does not buy from that seller again.

Can a seller talk the model into a pass?

The model has no pass to give. The worst a seller can do is skew the extracted claims, and a promise with no count claim fails closed as "unverifiable". Live injection results from scripts/serv_eval.mjs are published in the write-up.

What is a seller record?

Each seller origin has a record. It starts in good standing. A failed check (dispute) or a promise with nothing to check (unverifiable) puts the seller on hold, with the receipt that caused it. A human can release a hold after review. It does not refund the first payment.

Does real money move?

No. Tare runs on Kite testnet with pieUSD from the faucet. No USDC, no card.
