The label is not the delivery. Tare counts.

Tare is a buyer agent for x402 data sellers on Kite testnet. It pays, reads what the seller says it delivered, counts what actually arrived, and refuses the next payment to any seller whose label does not match.

The problem

Agents pay first. Nobody checks the receipt. Until now.

With x402 the body arrives only after payment. A seller can write "1,240 unique records, no nulls" and send 860 unique rows with gaps. The agent has already paid. Tare cannot claw that back, but it can make sure it is the last time.

Who decides

Three systems.
Strict lanes.

The model reads. The code judges. The wallet pays. None of them can do another's job.

SERV Reasoning

Reads the label

  • Extracts four typed claims from the prose
  • Treats the prose as untrusted data
  • Never sees the rows
  • Never returns a verdict
  • Never pays
Tare code

Counts and decides

  • Counts rows, unique ids, fields, nulls
  • Compares claims to measurements
  • Blocklists the seller's origin
  • Never asks the model for a verdict
  • Never invents a hash
Kite Passport

Pays, within limits

  • Capped session: 0.05 per tx, 1 total
  • Returns the settlement hash
  • Never called for a blocklisted seller
  • Passkey approval stays human

Guarantees

Built to fail closed.

Refused before paying

A blocklisted origin is stopped before kpass is ever called. The console's kpass counter does not move.

No claim, no pass

A label with no count claim is "unverifiable", not clean. Steering the model into nulls gets a seller held, not paid.

Never invents a hash

Only a settlement hash returned in PAYMENT-RESPONSE is stored or shown. Missing means "paid, no hash", never a made-up value.

Rows never reach the model

SERV sees the prose inside <prose> tags and nothing else. Any tags the seller hides in the prose are stripped.

One request, one payment

Every buy carries a request id. A double click replays the stored receipt instead of paying twice.

One buy at a time

Buys run in a single queue, and a payment left pending after a crash blocks that seller until a human looks.

FAQ

Questions,
answered plainly.

Does real money move?

No. Tare runs on Kite testnet with pieUSD from the faucet. No USDC, no card.

Does SERV decide whether to pay?

No. SERV Reasoning (gpt-5.4-mini-serv-multipath) only extracts four claims from the seller's prose. Counting, comparing, blocklisting and paying are all plain code. Any extra field the model returns, such as a "verdict", is dropped unread.

Why does Tare pay before checking?

Because x402 only returns the body after payment. There is nothing to count before paying. Tare's promise is about the next payment: a seller whose label failed is never paid again.

Can a seller talk the model into approving?

The model has no approval to give. The worst a seller can do is skew the extracted claims, and a label with no count claim fails closed as "unverifiable". Live injection results from scripts/serv_eval.mjs are published in the write-up.

What does a dispute actually do?

It records the evidence (settlement hash, body hash, prompt hash, claims and counts) and blocklists the seller's origin, so the next buy is refused before kpass. It does not refund the first payment.

Why is the hosted console read-only?

Kite Passport asks a human to approve the session with a passkey, and that step is never automated. The hosted site shows the receipts from a published local run.
